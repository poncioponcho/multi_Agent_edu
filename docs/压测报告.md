## 三、发现 1：并发丢更新（P0，已修复）

### 现象

`LearnerModel.UpdateMastery` 内部先调用 `GetState` 取得 `*KnowledgeState` 指针（该调用内部持锁），但**随后的读-改-写全部在锁外执行**：

```go
// 修复前 learner.go:72
func (m *LearnerModel) UpdateMastery(knowledgeID string, isCorrect bool) *KnowledgeState {
	state := m.GetState(knowledgeID)   // ← 只在取指针时持锁
	pL := state.Mastery                // ← 以下全在锁外
	...
	state.Mastery = ...
	state.Attempts++
	return state
}
```

同一 learner + 同一知识点的两个并发提交会读到同一个旧 `Mastery` 并互相覆盖 —— 经典 **lost update**，**静默丢数据，不报错**。

### 实测证据

```
# 8 goroutine × 200 次提交，全部提交同一 learner 的同一知识点
--- FAIL: TestUpdateMasteryConcurrentLostUpdate
    lost update: Attempts=1540, want 1600 —— 丢失了 60 次提交（3.8%）
    lost update: CorrectCount=788, want 800

# 对照组（每个 goroutine 操作独立知识点）通过 → 证明原因是同 key 的 RMW 竞争
--- PASS: TestUpdateMasteryConcurrentDistinctKnowledgePoints
```

`-race` 报 **13 条 DATA RACE**，涉及 `learner.go` 第 74/80/81/85/95/96/97 行（`Mastery` 读、`CorrectCount++`、`Streak++`、`Mastery` 写、`Attempts++`、`LastAttempt` 写）。

### 修复

1. 新增内部 `getStateLocked()`，要求调用方已持写锁（`sync.RWMutex` 不可重入，避免自死锁）；
2. `UpdateMastery` 把**整个 RMW 放进同一把写锁**内；
3. `GetState` / `UpdateMastery` / `GetWeakPoints` 一律**返回快照副本**，不再把内部指针交给调用方（否则指针逃逸后照样竞争）；
4. 新增只读的 `Mastery(id)` 访问器，API 层 `/next-topics` 改用它 —— 原先用 `GetState` 会让每个 GET 请求为全部知识点创建条目并反复取写锁，属**读接口写放大**。

### 修复后验证

```
--- PASS: TestUpdateMasteryConcurrentLostUpdate      # Attempts 精确 = 1600
--- PASS: TestUpdateMasteryConcurrentDistinctKnowledgePoints
--- PASS: TestGetStateConcurrentReadWrite
WARNING: DATA RACE 出现次数：13 → 0
评测指标未变：guidance=100.0% hint=100.0% alert=100.0% avgTurns=3.0   # 行为等价
```

## 四、发现 2：EngagementAgent 无锁读（P0，已修复）

修复发现 1 后用 `-race` 跑全量测试，**暴露出第二处同源缺陷**——评测框架（`internal/eval`）就足以触发：

```
WARNING: DATA RACE
Write at ... by goroutine 58:
  agent.(*EngagementAgent).trackSubmission()   agents.go:451  ← consecutiveCorrect++
Previous read at ... by goroutine 54:
  agent.(*EngagementAgent).analyze()           agents.go:463  ← 读 consecutiveErrors
```

`getEngagement()` 在锁内返回指针后，`trackSubmission` 会加锁改写，而 `analyze` **完全无锁**地读 `consecutiveErrors` / `consecutiveCorrect` / `recentResults`。

**修复**：`analyze` 改为基于 `snapshotEngagement()` 返回的一致快照判断（顺带修掉了 `recentResults` 为空时 `0/0 = NaN` 的隐患）。

> 值得注意：这一缺陷**功能测试完全测不出来**——18/18 用例、引导率 100% 全部通过，只有 `-race` 能发现。项目此前从未在 `-race` 下跑过测试，建议纳入常规回归。

## 五、发现 3：EventBus 吞吐悬崖与无界增长（P0，待改造）

### 5.1 吞吐悬崖：5000 是断崖点

`BenchmarkPublish` 在不同事件量下的吞吐（同一台机器）：

| 累计事件数 | ns/op | events/s |
|---|---|---|
| 1,000 | 804.0 | **1,243,781** |
| 3,000 | 768.2 | 1,301,744 |
| 5,000 | 913.4 | 1,094,811 |
| 8,000 | 16,598 | 60,248 |
| 20,000 | 60,072 | 16,647 |
| 50,000 | 149,192 | **6,703** |

**拐点精确落在 5000**，即 `MaxSeenEntries`。5000 → 50000 事件，吞吐从 109 万/s 跌到 6703/s，**降 163 倍**。

**根因**（`eventbus.go:113-123`、`138-148`）：去重表一旦达到 5000 条，`cleanSeenLocked()` 就会在**每一次** `Publish` 时全表遍历找过期项，而且这一切都在 `b.mu.Lock()` **写锁内**。由于只清理 5 分钟前的记录，压测期间一条都删不掉 —— 表只增不减，遍历成本只升不降。

隔离验证（`BenchmarkPublishSeenTableCost`）：

| 去重表预置条数 | ns/op | 说明 |
|---|---|---|
| 1,000 | 65,765 | 低于阈值，不触发清理 |
| 20,000 | **181,416** | 超阈值，每次发布都全表遍历 |

### 5.2 并发完全无效：写锁把发布串行化

```
BenchmarkPublish-10           20000   59,292 ns/op
BenchmarkPublishParallel-10   20000   58,972 ns/op   ← 并发发布毫无收益
```

并行基准与串行**几乎完全一致**，说明写锁 + 锁内清理把发布路径彻底串行化了，**加核无用**。

### 5.3 无界增长：内存与 goroutine

`history` 只追加、从不淘汰（`eventbus.go:122`），去重表同理。

```
发布 20000 个事件：history=20000, seen=20000
HeapAlloc 增量：12.30 MB（≈ 645 bytes/事件，且永不释放）
外推：1000 万事件后 history 常驻约 6150 MB
```

goroutine 无上限（`dispatch` 为每个事件、每个 handler 各起一个 goroutine，`eventbus.go:169`）：

```
基线 goroutine=4，灌入 3000 事件 × 5 handler 后峰值=15005
峰值/基线 = 3751 倍；理论上限 events×handlers = 15000   ← 完全吻合，无任何限流
```

### 5.4 读接口随 history 线性劣化

`GetHistory` / `GetTrace` 全量扫描 `history` 且持读锁，与 `Publish` 的写锁互斥：

| history 长度 | GetHistory | GetTrace |
|---|---|---|
| 1,000 | 2,883 ns / 3.9 KB | 3,345 ns |
| 5,000 | 15,657 ns / 16.2 KB | 15,725 ns |
| 20,000 | **57,098 ns / 65.4 KB** | **66,038 ns** |

严格 O(n)。20,000 条历史时，一次 `GET /events` 要 **57 µs 且分配 65 KB** —— 1000 QPS 就是 65 MB/s 的垃圾产生。

### 5.5 改造建议

| 优先级 | 措施 |
|---|---|
| **最高** | `history` 与 `seen` 改为**环形缓冲 / TTL 淘汰**（固定容量上限），让清理成本 O(1) 且不随运行时间增长 |
| **最高** | 去重表清理**移出写锁**：改用分片锁（sharded map）或后台 goroutine 定期清理，避免在关键路径上做全表遍历 |
| 高 | `history` 换为 ring buffer，`GetHistory`/`GetTrace` 改为按 correlation_id 建**索引**，避免全量扫描 |
| 高 | goroutine 数量加**信号量 / worker pool 限流**，避免流量洪峰直接打爆调度器 |
| 中 | `Publish` 增加背压策略（当前 channel 满即阻塞 HTTP 请求，且无超时） |
| 中 | `cmd/main.go` 的裸 `http.ListenAndServe` 补上 `ReadTimeout`/`WriteTimeout`/`IdleTimeout` 与限流 |

> 补充实测：事件通道**不是**瓶颈 —— 压测期间队列峰值仅 **1**（容量 1000）。真正的瓶颈在 `Publish` 侧的锁内清理，而不是消费端。这一点与最初的直觉相反，是靠采样 `queue_len` 才确认的。

## 六、发现 4：BM25 检索器成本（P1，待改造）

### 6.1 单次检索成本高得离谱

```
BenchmarkSearch-10                       425,307 ns/op   702,228 B/op   16,877 allocs/op
BenchmarkTokenize-10                      11,151 ns/op    15,800 B/op      601 allocs/op
```

**单次检索 425 µs，产生 702 KB 垃圾、16,877 次对象分配。** 而 Tutor Agent **每次生成回复都会调用一次**（`agents.go:178` / `238`）。

按 800 req/s 估算，仅检索一项就是 **562 MB/s 的分配速率** —— 这直接解释了压测中观察到的堆内存冲到 119 MB、GC 频繁触发。

**根因**（`bm25.go:91-100`、`123-131`）：`Search` 对每个 query token 遍历全部文档，而 `termFreq` 内部又对整个文档**重新 tokenize 一遍**。既没有倒排索引，也没有缓存切词结果。

### 6.2 语料扩充会灾难性劣化

```
BenchmarkSearchByCorpusSize/corpus=8-10       405,742 ns/op    687,843 B/op    16,535 allocs/op
BenchmarkSearchByCorpusSize/corpus=100-10   5,181,286 ns/op  8,604,615 B/op   206,555 allocs/op
BenchmarkSearchByCorpusSize/corpus=1000-10 51,163,468 ns/op 85,889,883 B/op 2,064,026 allocs/op
```

语料 8 → 1000 篇（125 倍），检索耗时 **405 µs → 51 ms（126 倍）**，是**超线性**劣化。1000 篇时单次检索 51 ms，单核上限仅约 20 次/秒。

**结论**：教材库一旦从 8 篇扩充到百篇量级，RAG 就会成为整个系统的绝对瓶颈。这在面试里是一个很好的"我知道我的系统在什么规模会崩"的答案。

### 6.3 改造建议

| 优先级 | 措施 |
|---|---|
| **最高** | 建**倒排索引**（token → posting list），把 `termFreq` 的重复切词彻底消除 |
| **最高** | 文档切词结果**在索引构建期缓存**（`docTokens[i]`），检索期只做 token 匹配 |
| 高 | 检索结果按 `(query, topK)` 加 LRU 缓存 —— 教育场景 query 重复率很高 |
| 中 | 引入 IDF 剪枝：`df == 0` 的 token 已在跳过，可进一步跳过 `idf` 过低的 token |

## 七、瓶颈分层定位（实验 C）

同样并发 100、每级全新实例，对比三个接口：

| 接口 | 吞吐 req/s | p50 | p99 | goroutine 峰值 | 相对成本 |
|---|---|---|---|---|---|
| `/api/v1/health`（纯 HTTP，不经总线） | **123,951** | 603 µs | 3.4 ms | 193 | 1× |
| `/api/v1/retrieve`（BM25，不经总线） | 5,464 | 14.1 ms | 76.2 ms | 198 | 慢 23× |
| `/api/v1/submit`（经事件总线全链路） | **708** | 117.5 ms | 203.2 ms | 747 | **慢 175×** |

并发 400 时：`/health` 104,043 req/s，`/retrieve` 6,120 req/s。

**结论**：
- HTTP 层本身能跑 **10 万+ QPS**，**不是瓶颈**；
- 瓶颈**确定在事件总线路径**（含 Agent 级联处理与 BM25 调用）；
- goroutine 峰值 ≈ **7.5 × 并发数**，即每个在途请求额外拉起约 7 个 goroutine。

**事件放大比**：并发 100 阶段 history 增长 38,499，同期约 4,250 个请求 → **约 9~11 个事件 / 每次提交**。一次用户提交会触发 Assessment → Tutor / Curriculum / Engagement 的完整级联。

## 八、吞吐与延迟总览

### 实验 A：单实例连续阶梯（暴露"随时间劣化"）

`-stages 10,50,100,200,400 -duration 6s -learners 200`

| 并发 | 吞吐 req/s | p50 | p90 | p99 | max | 错误 | gorout 峰值 | 内存 MB |
|---|---|---|---|---|---|---|---|---|
| 10 | 706 | 14.6 ms | 16.2 ms | 21.7 ms | 47.6 ms | 0 | 77 | 41.2 |
| 50 | 453 | 117.2 ms | 136.3 ms | 180.3 ms | 180.8 ms | 0 | 356 | 59.3 |
| 100 | 367 | 282.4 ms | 295.6 ms | 310.0 ms | 314.6 ms | 0 | 706 | 64.4 |
| 200 | 354 | 597.9 ms | 691.2 ms | 746.2 ms | 760.2 ms | 0 | 1406 | 83.3 |
| 400 | 363 | 947.3 ms | 1.35 s | 1.37 s | 1.37 s | 0 | 2806 | 119.7 |

**错误数全程为 0** —— 系统不会快速失败，只会**悄悄变慢**。这是比崩溃更危险的失效模式。

**逐秒吞吐**（同一并发下、负载不变，仅时间推移）：

```
并发 10 : 949 730 682 645 641 591   | 首秒 → 第3秒：-28%
并发 50 : 682 526 415 383 372 351   | 首秒 → 第3秒：-39%
并发 100: 464 361 346 352 343 346   | 首秒 → 第3秒：-25%
并发 200: 474 416 335 331 282 300   | 首秒 → 第3秒：-29%
```

**并发 10 时，6 秒内吞吐就从 949 掉到 591（-38%），负载没有任何变化。** 这就是 5.1 节去重表膨胀在真实服务上的直接体现。

资源增长：`history 25,532 → 106,447`（+80,915，只增不减）；堆 `26.9 MB → 119.7 MB`（+92.8 MB）。

### 实验 B：每级全新实例（真实饱和曲线）

排除"运行时间"这个混淆变量后，用全新实例跑每一级：

| 并发 | 吞吐 req/s | p50 | p90 | p99 | gorout 峰值 |
|---|---|---|---|---|---|
| 10 | 809 | 13.7 ms | 15.5 ms | 21.2 ms | 75 |
| 50 | 826 | 67.2 ms | 75.2 ms | 100.0 ms | 371 |
| 100 | 814 | 135.0 ms | 153.4 ms | 165.4 ms | 752 |
| 200 | 800 | 266.7 ms | 314.3 ms | 342.6 ms | 1495 |
| 400 | 735 | 571.4 ms | 667.2 ms | 781.0 ms | 3199 |
| 800 | 710 | 1.05 s | 1.34 s | 1.36 s | 6689 |

**并发 10 就已经达到吞吐上限（809 req/s）。并发加到 800（80 倍），吞吐不变（710 req/s），延迟线性涨 76 倍。**

这是"硬串行点 + 单实例 CPU 饱和"的典型特征：系统在极低并发下就已打满，之后所有追加的并发只转化为排队等待。

**两个实验共同说明**：这个系统有两层问题 ——
1. **天花板低**（实验 B）：~800 req/s，与并发无关；
2. **还会随时间劣化**（实验 A）：同负载下吞吐持续下降。

## 十、面试要点提炼

**最值得讲的一条故事线**（有实测、有根因、有修复、有验证）：

> 我原本以为系统最大的风险是 LLM 调用慢，但压测后发现真正的瓶颈在事件总线：吞吐被钉死在 800 req/s，并发从 10 加到 800 完全没有增长。
>
> 更关键的是，我在写并发回归测试时发现 `UpdateMastery` 的读-改-写在锁外执行 —— 1600 次并发提交只记到 1540 次，**静默丢了 3.8% 的学习数据，而且不报任何错**。修掉之后用 `-race` 跑全量测试，又暴露出 `EngagementAgent` 有同源的缺陷，这个连 18/18 的功能用例都测不出来。
>
> 还有一个反直觉的发现：我本来怀疑事件通道满了会阻塞 HTTP 请求，但采样 `queue_len` 发现峰值只有 1 —— 真正的瓶颈是 `Publish` 在**写锁内**全表遍历去重表。这个清理成本随运行时间线性增长，所以并发 10、负载不变的情况下，6 秒内吞吐就掉了 38%。**只报平均吞吐是看不见这个现象的，必须做逐秒分桶。**
>
> 另外 BM25 检索器单次要 425 µs、产生 702 KB 垃圾，教材库从 8 篇扩到 1000 篇耗时涨 126 倍 —— 所以我很清楚这个系统的规模边界在哪。

**可延伸追问的准备**：
- *为什么不直接上 k6/wrk？* —— 需要同步抓服务端 goroutine/内存/总线积压才能把"吞吐下降"和"资源泄漏"关联起来，而且要逐秒分桶，通用工具做不到；顺带也符合项目"零第三方依赖"的定位。
- *为什么去重表设计成这样？* —— 原意是防事件风暴，但用"全表遍历 + 写锁内清理"实现，把防抖措施本身变成了性能悬崖。正确做法是固定容量环形结构 + 后台清理。
- *如果让你改，先改哪个？* —— 先给 `history`/`seen` 加容量上限（一行配置就能止住时间维度的劣化），再建倒排索引（天花板提升一个数量级），最后才考虑加机器 —— 因为当前加核完全无效。
